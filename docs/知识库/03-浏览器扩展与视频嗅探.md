# 浏览器扩展逆向 + 网页视频嗅探设计空间

用户第一优先级需求（「网页插件要能在网页上下载任何视频」）的可行性分析。

## 1. gopeed 官方浏览器扩展（upstream/browser-extension @v1.1.5）

    技术栈：Plasmo 0.89.4 + React 18 + MUI + @gopeed/rest + @plasmohq/storage [S:package.json]
    权限：downloads, webRequest, nativeMessaging, notifications, contextMenus；
          host_permissions http/https 全量 [S:package.json manifest 块]
    接管手法：chrome.downloads.onDeterminingFilename（Chrome）/ onCreated +
              webRequest.onHeadersReceived（Firefox 拿 size）拦截浏览器下载，
              去重后转成 gopeed 任务（client.createTask）[S:background/index.ts:324-393,549-598]
    与客户端通信：nativeMessaging（找本机 gopeed）+ HTTP + token（用户在 options 页手填）
    右键菜单：链接/图片/视频/页面 发送到 gopeed [S:background/index.ts:44-53]

    关键结论 [S]：**官方浏览器扩展不做视频嗅探**。它只接管「浏览器已经要下的东西」。
    gopeed 的视频解析能力其实在「JS 扩展（onResolve）」里，靠 goja 脚本按站点适配，
    而那套要求 git 安装 —— 这正是它「普通用户下不了视频」的结构性原因。
    => Sun_Tey 的差异化必须做在扩展内的嗅探层，而不是复制 gopeed 的接管层。

## 2. IDM Integration Module（upstream/idm-ext/IDMGCExt @6.43.1，crx 解包）[B]

    manifest（明文，证据充分）[S:manifest.json]：
      MV3；content_scripts 匹配 *://*/* 且 all_frames + run_at document_start
      权限 17 项：scripting tabs cookies contextMenus webNavigation webRequest
        declarativeNetRequest downloads downloads.shelf downloads.ui management
        storage proxy nativeMessaging（+ optional notifications/system.display）
      native messaging：com.tonec.idm -> IDMMsgHost.exe，allowed_origins 锁死两个扩展 ID
        （Internet Download Manager\IDMMsgHost.json 原文可查）
    代码（background.js 56KB / content.js 29KB 已压缩混淆）：只能做结构性判读 [I]
      - 扫 DOM 里的 video 元素与 source 子元素，用 getBoundingClientRect + getComputedStyle
        过滤不可见/零尺寸元素（不碰隐藏播放器）
      - 针对特定播放器取内部元数据（代码里出现 coreVideoPlayerMetaData.videoFBID、
        player.vimeo.com/video/(\d{2,}) 之类模式）=> 站点专用播放器探针
      - 收集 a[download]/a[href] 批量列表，附 download 属性与链接文本（"下载全部"面板）
      - 与本地宿主用自定义 accept 头 application/vnd.t1c.int-N 通信
    行为面（tips.txt 原文，官方表述）[S]：
      「按文件扩展名列表接管任意浏览器的下载」；按住修饰键强制接管/ALT 放弃接管；
      完成后对话框、启动对话框、进度对话框都可关；站点账号密码可存（Sites Logins）
    可借鉴（行为，不是代码）：
      1) 扩展必须能在「没找到视频」时静默，出现时才给按钮（IDM 就是这个体感）
      2) 修饰键覆盖接管策略（防误伤）
      3) 文件类型列表 = 接管开关，且可在客户端设置（用户不需要在扩展里配）
      4) 与本地程序通信要有一个专用宿主（本机是 loopback HTTP + token，等价物）

## 3. 网页视频「能下」与「不能下」的技术边界（必须对用户诚实）

| 类型 | 可否 | 手法 | 备注 |
|---|---|---|---|
| 直链 mp4/webm/mkv/ts（video.src 是 http URL） | ✅ | 直接交给内核多线程下 | 带 Referer/Cookie 才不 403 |
| HLS（.m3u8，无 DRM） | ✅ | 解析清单+并发分片+AES-128 解密+合并/remux MP4 | 前代实现 hlsx 已实现 |
| MPEG-DASH（.mpd，无 DRM） | ⚠️ 未做 | 需 XML 解析 + 音视频双轨合并 | gopeed/前代实现 都没有；Sun_Tey 待评估 |
| MSE + blob: URL | ❌ 不能按 URL 下 | blob 是页面内存对象，扩展拿不到字节 | 只能：抓它背后的媒体请求分片（常是 fmp4 init+segment，可重组）|
| fMP4（init.mp4 + *.m4s，无 DRM） | ⚠️ 可实现 | 嗅探 init+segments 列表，按 DASH/HLS 规则拼接后 remux | 中等难度，收益高（B 站/YouTube 都用） |
| DRM（Widevine/FairPlay：License URL + 密文） | ❌ 明确不做 | 需要解密私有实现 | 法律与道德边界；写进 README |
| 网页录制兜底 | ⚠️ 理论可行 | getDisplayMedia 录屏（用户可见、有权限弹窗） | 不是「下载」，画质与效率差，非首选 |

    结论：「任何视频」= 上面 ✅ + ⚠️ 全做完，覆盖绝大多数场景；DRM 类必须在 UI 里
    明确提示「该站点使用加密流，无法下载」，而不是让进度条假装在跑（gopeed 的差评点）。

## 4. Sun_Tey 扩展的分层设计（写入施工图）

    L1 接管层（IDM/gopeed 已有）：chrome.downloads.onDeterminingFilename + 文件类型列表 + 修饰键
    L2 嗅探层（核心差异）：
        - performance.getEntriesByType('resource') 扫描媒体后缀与 content-type
        - MAIN world 注入 hook fetch/XHR/HTMLMediaElement.src/URL.createObjectURL/MediaSource
          （把 MSE 背后的真实请求段号记录下来）
        - MutationObserver 监听动态插入的 <video>/<source>（前代实现 已有基础版）
        - 规则表内置进扩展（可按域名给不同规则），不依赖任何 git 安装
    L3 呈现层：<video> 悬浮下载按钮 + 页面级「媒体列表」面板（多码率/多语言合并展示）
    L4 传输层：loopback HTTP + token（复用 前代实现 免 token handshake 自动配好，
        避免 gopeed「手填地址和令牌」的最大体验痛点）
    L5 失败提示：识别 DRM 特征（license 请求 / keySystem）-> 明确告知不可下

    安全红线：host_permissions 全量 + 读 Cookie 是这类工具的行业常态（IDM 就这么干），
    但开源项目要把「发给本地的字段」白名单化（url/referer/UA/必要 cookie），
    并禁止把页面内容上传任何远端。
