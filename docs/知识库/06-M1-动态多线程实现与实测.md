# 06 — M1 动态多线程：实现要点、实测与踩坑

> 来源：M1 施工（2026-11-23）。事实来源是本仓库 `core/internal/download/httpx/` 的实现与
> `scripts/bench_multithread.py` 的实测输出。证据标记沿用 KB 约定。
> 与 01 号文档的关系：01 是 gopeed 上游**行为**的逆向（`[S]`），本篇是 Sun_Tey 按行为**重新实现**
> 之后的落地结论与实测数字（`[V]`）。没有复制上游源码（GPL-3.0 隔离，见规则 §2）。

## 1. 三个独立旋钮（aria2 语义，实测有效）

| 旋钮 | 默认 | 语义 | 实测证据 |
|---|---|---|---|
| `MinSplitSize` | 4 MiB | 文件小于 2× 它 → 整文件单连接；并且 `legs ≤ size / MinSplitSize` | 32 MiB 文件即使 `-conns 16 -max-per-host 16` 也只跑到 8 路等效（8.02x），因为 32/4=8 `[V]` |
| `MaxConnPerHost` | 8 | 单服务器并发上限（aria2 `-x`） | 64 MiB、单连接限速 8 MiB/s 时，16 路并不比 8 路快（5.62x vs 5.65x）`[V]` |
| `MaxConns` | 16 | 整个内核的总连接预算（aria2 `-s`），进程级 FIFO 令牌 | 多任务并发由 `connPool` 统一发放，单任务不能挤爆整机 `[S]` |

另加两个"分片粒度"旋钮：`SegmentsPerLeg`（默认 8，一条连接平均领几段，**扇出 >1 才能偷块**）、
`MaxSegments`（默认 512，限制快照大小）与 `SegmentFloor`（默认 1 MiB，切分后单段下限）。

**结论**：段大小 = `size /(legs × SegmentsPerLeg)` 再夹到 `SegmentFloor` 以上并向上取整到 MiB，
段数 = `ceil(size/段大小)`。**"一段一连接"的静态布局永远做不了再平衡**——这是前代实现与动态
实现的分水岭，也是断点续传契约必须连布局一起存的原因（见 §6）。

## 2. 慢启动扩连（gopeed 行为，重新实现）

* 批大小 `1→2→4→16→256`（`nextBatch`：`batch≤1` 特判成 2，否则 `batch²`，>16 直接开到上限，全程 cap 到 `max`）。
* `opened()` 在发出请求前 +1；**响应头到达**就 `confirmed()`（不等 body），失败走 `failed()`。
  两条路径都必须递减 `pending`，否则一条死连接就把整条 ramp 冻住。
* 只有 `pending == 0` 时才扩张 `allowed`：一波全部有响应，才允许下一波。
* 429/503 → `throttled(cooldown)`：`pausedUntil` 之内**不扩张**，并按 `Retry-After` 等待
  （`TestThrottle429HonoursRetryAfter` `[V]`）。

## 3. 慢连接偷块（真正的差异化）

* 每段一个 `lastProgNano` 原子时间戳，`stream` 每写一个缓冲打一次点（无锁）。
* reporter 每 500 ms 扫一遍：**只有队列已空且仍有未完成段**时才偷（尾部效应场景）。
* 受害者条件：有人正在取 && 剩余 ≥ 2×`stealMinChunk` && 停顿 ≥ `stealThreshold`（默认 3 s）
  && 该段偷窃次数 < `StealMaxPerChunk`（默认 8，防乒乓）。
* 动作：只 cancel **这一条** attempt 的 context（不动 run ctx），段回到队列，空闲腿接手；
  发 `steal` 事件，带中文说明（"慢连接：分块 N 已 x s 无进展（剩余 y），转交更快的连接"）。

**实测**（`TestStealHandoverSlowLeg`）：服务器对第 4 段的**首个**请求挂 1500 ms。
偷块生效后 1.001 s 完成、该段被取 2 次、字节级一致 `[V]`。

## 4. 踩过的坑：连接槽位重复申请（M1 验收 bug）

`legWorker` 原来在**每取一段之前**都调用 `slowStart.acquire()`，而 `active` 只在 goroutine
退出时 `exit()` 递减。于是"跑完自己那段"的腿会永远停在 `acquire` 队列里：

* `idleCount()==0` → 偷块逻辑**永远不会触发**（表象：慢连接明明存在，却不偷）；
* 更严重：**任何"段数 > 连接数"的任务**都会在"每腿一段"之后彻底停住。

正确语义是**一条腿终身一个槽位**（函数注释本来就写着 finishing a segment never releases the
slot，代码没做到）。改法：`acquire` 只在整个 `legWorker` 开头调用一次。修复后
`TestStealHandoverSlowLeg` 由 FAIL 转 PASS `[V]`。

> 记这条是因为它是**注释与实现不一致**的典型：只读注释会以为行为已经对了。判据必须实测。

## 5. 实测方法论（为什么必须限速）

纯回环不限速时一条连接就能打满，**多线程"看起来没收益"**，这会误导判断。真实 CDN 的行为是
**按连接限速**，所以基准服务器必须限速（`--limit KiB/s`），那才是 IDM/迅雷多线程的战场 `[V]`。

脚本：`scripts/bench_multithread.py`（内置 Range + 按连接限速服务器 + SHA-256 一致性判定），
驱动器：`core/cmd/suntey-bench`（绕过 dispatcher/store，直接压 `httpx.Downloader`）。

| 连接数 | 中位 MB/s | 相对 1 路 | 说明 |
|---:|---:|---:|---|
| 1 | 3.84 | 1.00x | 单连接限速 4 MiB/s |
| 8 | 27.42 | 7.14x | 近似线性 |
| 16 | 47.13 | 12.27x | 放开 `MaxConnPerHost` 后继续涨 |

（96 MiB 文件、2 次、三种连接数落盘 SHA-256 完全一致；完整三组表见 `docs/验收报告/M1.md`。）

两个**看起来像 bug 其实是设计**的封顶：`MaxConnPerHost=8`（默认）与 `legs ≤ size/MinSplitSize`。
要复现 16 路，必须同时给大文件与 `--max-per-host 16`。

## 6. 给后续里程碑的话

* **M1.5 续传**：段布局是**计划的一部分**（连接数一变就重排），所以快照必须同时存
  layout + 每段已完成字节（`RunOptions.Persist(total, []model.ChunkState)` 已是这个形状）。
  只存计数量的旧形状会让续传重下已经在盘上的字节。
* **M5 UI**：`steal` 与 `slow` 是独立事件类型，UI 能直接显示"哪条连接被判为慢连接"，
  这是迅雷没有的可解释性。
* **M8 设置**：三个旋钮都应可配（连接数/单服务器上限/最小分片），但默认值必须是
  "装好就能用"的 8/16/4 MiB，不许用户先读书。
